9:Tdd82,<p>You've installed a web app on your phone. You close it. You lock your screen. Ten minutes later - <em>buzz</em> - a notification pops up: "New message from Alex." You tap it, and the app opens right where you need it.</p>
<p>How did that work? The web app wasn't running. There's no native code. No APNs. No Firebase Cloud Messaging (well, not directly). Just... a website. Yet somehow it reached through your locked screen and tapped you on the shoulder.</p>
<p>This is <strong>Web Push</strong> - a set of open web standards that give web applications the same background notification superpower that native mobile apps have had for over a decade. It's the technology that makes Progressive Web Apps (PWAs) feel genuinely <em>native</em>.</p>
<p>This post explains what Web Push is, who the players are, and exactly how a message travels from your server to a user's locked phone - with diagrams, analogies, and no hand-waving.</p>
<hr>
<h2>📬 The Problem: Web Apps Can't Ring the Doorbell</h2>
<p>Here's the fundamental issue. A web app's JavaScript runs <strong>only</strong> when the page is open. Close the tab, and everything stops. There's no background thread, no persistent socket, no daemon watching for updates.</p>
<p>Compare this with native apps on your phone. When WhatsApp or Gmail sends you a notification, the OS-level push infrastructure (APNs on iOS, FCM on Android) wakes the app in the background, delivers a payload, and triggers a notification - all without the app being actively running.</p>
<p>For years, web apps were stuck in the <strong>pull</strong> world: the app had to be open to ask, "Anything new?" If the user closed the tab, the app went silent. There were hacks - long polling, WebSockets - but they all depended on the page being alive.</p>
<p>Web Push changes this. It gives web apps a way to <strong>push</strong> information to the user even when the browser tab is closed, the browser is minimized, or on mobile, the PWA is completely suspended.</p>
<figure class="mermaid-diagram"><img src="/diagrams/web-push-explained-diagram-1.svg" alt="Diagram 1"></figure>
<p>The critical insight: <strong>your server never talks directly to the user's browser</strong>. There's always a middleman. And that middleman is the key to everything.</p>
<hr>
<h2>🏗️ The Three Players: Server, Push Service, Service Worker</h2>
<p>Web Push isn't a single API call. It's a coordinated system with three distinct roles, each with a specific job:</p>
<h3>1. Your Application Server (The Sender)</h3>
<p>This is your backend - the thing that decides "User X needs to know about this." It could be a Node.js server, a Go service, a Python backend, whatever. When an event happens (a new message, a task assignment, a price drop), your server is the one that initiates the push.</p>
<h3>2. The Push Service (The Middleman)</h3>
<p>This is the surprising one. Your server <strong>never</strong> connects directly to the user's browser. Instead, it sends the message to a <strong>push service</strong> - a web service operated by the browser vendor.</p>
<ul>
<li>Chrome uses Google's push service (at <code>fcm.googleapis.com</code>)</li>
<li>Firefox uses Mozilla's push service (at <code>push.services.mozilla.com</code>)</li>
<li>Safari uses Apple's push service</li>
</ul>
<p>You don't get to choose which push service is used. The browser decides. But here's the genius: it doesn't matter, because every push service speaks the same language - the <strong>Web Push Protocol</strong> (an IETF standard, <a href="https://www.rfc-editor.org/rfc/rfc8030">RFC 8030</a>). Your server makes one standardized HTTP POST request, regardless of which browser the user has.</p>
<h3>3. The Service Worker (The Receiver)</h3>
<p>A <strong>service worker</strong> is a special JavaScript file that runs in the background, separate from any web page. It has no access to the DOM, but it has something more important: it can be <strong>woken up by the browser</strong> even when no tab is open.</p>
<p>When the push service delivers a message to the browser, the browser wakes up the service worker and fires a <code>push</code> event. The service worker then calls <code>showNotification()</code> to display the notification on the user's screen.</p>
<figure class="mermaid-diagram"><img src="/diagrams/web-push-explained-diagram-2.svg" alt="Diagram 2"></figure>
<p>Think of it like a postal system: you (the server) write a letter and hand it to the postal service (the push service). The postal service has a permanent delivery route to the user's house (the persistent OS connection). The postal service drops the letter at the door, and the house's automated doorbell system (the service worker) rings the bell and shows the notification.</p>
<hr>
<h2>🔑 VAPID Keys: The Server's Passport</h2>
<p>Here's a security question: if anyone can make an HTTP POST to the push service, what stops a random attacker from spamming your users with fake notifications?</p>
<p>The answer is <strong>VAPID</strong> - <strong>Voluntary Application Server Identification</strong> for Web Push (<a href="https://datatracker.ietf.org/doc/html/rfc8292">RFC 8292</a>).</p>
<p>VAPID is like a passport for your server. It's a pair of cryptographic keys - one public, one private - that uniquely identify your application.</p>

























<table><thead><tr><th>Key</th><th>What It Is</th><th>Who Sees It</th></tr></thead><tbody><tr><td><strong>Public Key</strong></td><td>Your server's identity, like a passport number</td><td>Everyone - the browser, the push service</td></tr><tr><td><strong>Private Key</strong></td><td>Your server's secret proof of identity</td><td>Only your server - <strong>never</strong> exposed to clients</td></tr><tr><td><strong>Subject</strong></td><td>A <code>mailto:</code> or <code>https://</code> contact for the app operator</td><td>The push service (for operational contact)</td></tr></tbody></table>
<h3>How It Works</h3>
<ol>
<li>You generate a VAPID key pair <strong>once</strong> for your application (using tools like <code>npx web-push generate-vapid-keys</code>).</li>
<li>When the user subscribes to push, you pass the <strong>public key</strong> to the browser. The browser forwards it to the push service, which stores it alongside the subscription.</li>
<li>When you send a push message, you sign a <strong>JSON Web Token (JWT)</strong> with your <strong>private key</strong> and include it in the request headers.</li>
<li>The push service uses the stored public key to verify the JWT signature. If it matches, the message is authentic. If not, it's rejected.</li>
</ol>
<figure class="mermaid-diagram"><img src="/diagrams/web-push-explained-diagram-3.svg" alt="Diagram 3"></figure>
<p>The beauty of this system is that even the push service - which is controlled by Google, Mozilla, or Apple - <strong>cannot read your message payload</strong>. It can only verify that the message came from the right server. The payload is end-to-end encrypted between your server and the user's browser.</p>
<hr>

<p>Before you can send a push notification, you need the user's permission and their <strong>push subscription</strong> - a unique address that tells you how to reach that specific browser on that specific device.</p>

<h2>🚀 Sending a Push Message</h2>
<p>An event happens on your server - a new message arrives for User X. Here's what happens next.</p>
<h3>Step 1: Encrypt and Send</h3>
<p>Your server retrieves User X's stored subscription, then encrypts the payload using the browser's <code>p256dh</code> and <code>auth</code> keys. Since the push service is a middleman, Web Push uses <strong>end-to-end encryption</strong> (<a href="https://www.rfc-editor.org/rfc/rfc8291">RFC 8291</a>) so only the user's browser can read the message.</p>
<p>The process: your server generates ephemeral ECDH keys, computes a shared secret with the browser's public key, derives an encryption key via HKDF, and encrypts using AES-128-GCM. The push service only ever sees opaque bytes.</p>
<figure class="mermaid-diagram"><img src="/diagrams/web-push-explained-diagram-5.svg" alt="Diagram 5"></figure>
<p>In practice, libraries like <a href="https://github.com/web-push-libs/web-push">web-push</a> (Node.js), <a href="https://github.com/web-push-libs/pywebpush">pywebpush</a> (Python), or <a href="https://github.com/SherClockHolmes/webpush-go">webpush-go</a> (Go) handle the crypto, JWT signing, and HTTP formatting:</p>

<p>The library encrypts the payload, signs the VAPID JWT, sets headers (<code>Authorization</code>, <code>Crypto-Key</code>, <code>Encryption</code>, <code>Content-Encoding</code>, <code>TTL</code>, <code>Urgency</code>, <code>Topic</code>), and POSTs to the push service endpoint.</p>
<h3>Step 2: Delivery</h3>
<p>The push service validates your VAPID signature, then delivers the encrypted message over a <strong>persistent OS-level connection</strong> - the same always-on socket that native push systems (APNs, FCM) use.</p>
<p>This is the key insight: <strong>the push service maintains a permanent connection to every browser</strong>. Your server doesn't need to. You hand off the message, and the push service handles the last mile - even to a phone with its screen off. If the device is offline, the message stays queued until the device reconnects or the TTL expires.</p>
<p>The response tells your server what happened:</p>

























<table><thead><tr><th>Code</th><th>Meaning</th><th>Action</th></tr></thead><tbody><tr><td><code>201</code></td><td>Accepted and queued</td><td>Success</td></tr><tr><td><code>410</code></td><td>Subscription permanently invalid</td><td>Delete from your database</td></tr><tr><td><code>429</code></td><td>Rate limited</td><td>Retry after <code>Retry-After</code> header</td></tr></tbody></table>
<p>The <code>410</code> response is your <strong>self-cleaning mechanism</strong> - when a user uninstalls or clears browser data, the push service tells you automatically.</p>

<p>Notice how the <code>push</code> event handler <strong>must</strong> show a notification. Remember the <code>userVisibleOnly: true</code> contract? This is where it's enforced. If you receive a push and don't show a notification, the browser may revoke your push permission or show a generic "This site has been updated in the background" notification instead.</p>
<p>The <code>notificationclick</code> handler is your chance to control what happens when the user taps the notification. Typically, you focus an existing app window or open a new one.</p>
<p>The whole journey - from server event to notification on screen - typically takes <strong>under a second</strong> when the device is online.</p>

<h2>🔒 Security: Why This Design is Smart</h2>
<p>Web Push's architecture makes several smart security decisions:</p>
<p><strong>1. End-to-end encryption is mandatory.</strong> The push service cannot read your payloads. Even if the push service is compromised, the attacker gets encrypted bytes they can't decrypt. Only the user's browser has the private key needed for decryption.</p>
<p><strong>2. VAPID prevents spoofing.</strong> Without your private key, no one can impersonate your server. The push service cryptographically verifies every message.</p>
<p><strong>3. Subscription endpoints are capability URLs.</strong> The endpoint URL is effectively a secret - knowing it is sufficient to send a push to that user. This is why subscriptions should be stored securely and never logged or exposed in debug output.</p>
<p><strong>4. User consent is required.</strong> The browser enforces explicit permission. No background silent tracking. Every push must result in a visible notification (<code>userVisibleOnly: true</code>).</p>
<p><strong>5. Secure context required.</strong> The Push API only works over HTTPS. No exceptions.</p>

<p>A few important caveats:</p>
<ul>
<li><strong>iOS Safari</strong> requires the web app to be <strong>added to the Home Screen</strong> (installed as a PWA) for push to work. Push doesn't work in regular Safari tabs on iOS.</li>
<li><strong>WebView on Android</strong> does not support Push API - it works only in full browsers.</li>
<li>Each browser+device combination creates a <strong>separate subscription</strong>. Subscribing on desktop Chrome does not subscribe your phone. Each needs its own subscription.</li>
</ul>

<h2>⚡ Practical Tips</h2>
<p><strong>Keep payloads small.</strong> The Web Push spec guarantees at least 4KB, but smaller is faster and more reliable. Send just enough data to render the notification (title, body, tag), then let the app fetch full details when opened.</p>
<p><strong>Use <code>tag</code> for deduplication.</strong> If you send multiple notifications of the same type (e.g., new messages), give them the same <code>tag</code>. The browser replaces older notifications with the same tag instead of stacking them.</p>
<p><strong>Set appropriate <code>TTL</code>.</strong> A chat message should expire quickly (minutes). A task assignment might live longer (hours). A time-sensitive sale alert is useless after the sale ends. Match TTL to your content's shelf life.</p>
<p><strong>Handle <code>410 Gone</code> gracefully.</strong> When the push service tells you a subscription is dead, remove it immediately. Don't keep sending to stale subscriptions - the push service may rate-limit you.</p>
<p><strong>Re-upsert on app open.</strong> Every time the app opens and notifications are enabled, re-send the current subscription to your server. This handles the case where the browser silently rotated the subscription, and keeps your stored data fresh.</p>
<p><strong>Don't ask for permission too early.</strong> The biggest mistake: prompting for notifications the moment the page loads. Instead, wait until the user has context for <em>why</em> they'd want notifications, and trigger the prompt from an explicit button click.</p>
