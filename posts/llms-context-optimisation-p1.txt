1a:T3465,<p>As software engineers, we are accustomed to "stateless" systems. A REST API call comes in, we process it, and we forget it. It’s clean, deterministic, and scalable.</p>
<p><strong>LLM Agents are none of those things.</strong></p>
<p>Agents are stateful beasts. They "remember" by carrying around a massive, ever-growing baggage of text known as the <strong>Context Window</strong>. Before an agent can make a single decision, it must re-read every previous instruction, tool output, and user correction.</p>
<p>In this deep dive, we will strip away the hype of "1 Million Token Context Windows" and look at memory through the lens of <strong>System Engineering</strong>. We will explore how to stop treating context as a dumping ground and start treating it as a managed resource.</p>
<hr>
<h2>📉 The Physics of Attention: Why "More" is Less</h2>
<p>Before we write any code, let's understand the bottleneck we are dealing with.</p>
<p>We often assume that a larger context window means a "smarter" model. If I can fit 128k tokens, why not just dump the entire database schema, three PDF manuals, and the last 500 conversation turns into the prompt?</p>
<h3>The "Lost in the Middle" Phenomenon</h3>
<p>Research from both OpenAI and Anthropic shows that as context grows, <strong>reasoning quality degrades</strong>.</p>
<figure class="mermaid-diagram"><img src="/diagrams/llms-context-optimisation-p1-diagram-1.svg" alt="Diagram 1"></figure>
<ul>
<li><strong>Latency:</strong> Processing time scales linearly (or worse) with input length.</li>
<li><strong>Cost:</strong> You pay for every token, every single turn.</li>
<li><strong>Confusion:</strong> Conflicting instructions ("Context Conflict") and irrelevant details ("Context Noise") drown out the signal.</li>
</ul>
<p>This leads to what I call the <strong>Context Paradox</strong>:</p>
<blockquote>
<p>The more an agent "remembers," the slower and less accurate it becomes at using that memory.</p>
</blockquote>
<p>We need a strategy to solve this. We need <strong>Reshape and Fit</strong>.</p>
<hr>
<h2>✂️ Technique 1: Context Trimming (The Sliding Window)</h2>
<p>The most fundamental approach is to admit that not everything matters forever.</p>
<h3>The Mechanism</h3>
<p>This is the "FIFO" (First-In-First-Out) of memory management. You maintain a strictly bounded window of the most recent  turns.</p>
<ol>
<li><strong>New Message Arrives:</strong> Append it to the list.</li>
<li><strong>Check Length:</strong> Is <code>total_tokens > max_limit</code>?</li>
<li><strong>Trim:</strong> Drop the oldest messages (typically keeping the System Prompt pinned at the top) until you are back under the limit.</li>
</ol>
<figure class="mermaid-diagram"><img src="/diagrams/llms-context-optimisation-p1-diagram-2.svg" alt="Diagram 2"></figure>
<h3>When to Use It</h3>
<ul>
<li><strong>Stateless Tasks:</strong> Chatbots where previous turns rarely impact the current request.</li>
<li><strong>Low Latency:</strong> You need a predictable, constant cost per turn.</li>
</ul>
<p><strong>The Trade-off:</strong> It’s brutal. If the user defined a variable <code>x = 5</code> in Turn 1, and you trim it in Turn 10, the agent has amnesia.</p>
<hr>
<h2>🗜️ Technique 2: Context Compaction (The Tool Diet)</h2>
<p>For <strong>Agentic workflows</strong>, Trimming is often too aggressive. The real culprit in token bloat usually isn't the <em>conversation</em> - it's the <strong>Tools</strong>.</p>
<p>Imagine an agent searching for a file.</p>
<ul>
<li><strong>Agent:</strong> "List files in /logs"</li>
<li><strong>Tool Output:</strong> Returns 500 file names (3,000 tokens).</li>
<li><strong>Agent:</strong> "Read error.log"</li>
</ul>
<p>Once the agent has decided to read <code>error.log</code>, it <em>no longer needs</em> the list of the other 499 files. That 3,000-token block is now dead weight.</p>
<h3>The "Distill" Strategy</h3>
<p><strong>Context Compaction</strong> involves keeping the <em>flow</em> of the conversation but stripping the <em>payload</em> of older tool calls.</p>
<ul>
<li><strong>Before:</strong> Full JSON output of the <code>list_files</code> tool.</li>
<li><strong>After:</strong> A placeholder like <code>[Tool output: 500 files listed. Result: Success]</code>.</li>
</ul>
<figure class="mermaid-diagram"><img src="/diagrams/llms-context-optimisation-p1-diagram-3.svg" alt="Diagram 3"></figure>
<p><strong>Why This Matters:</strong>
It preserves the <strong>Reasoning Chain</strong> (the agent knows <em>why</em> it made a decision) without paying the <strong>Token Tax</strong> for data that has already been processed.</p>
<hr>
<h2>📝 Technique 3: Context Summarization (The Golden State)</h2>
<p>This is the most sophisticated approach, moving us from "forgetting" to "synthesizing."</p>
<p>Instead of dropping old turns, we periodically ask an LLM to "compress" the history into a structured <strong>Golden Summary</strong>. This summary is then injected back into the context, effectively becoming the agent's long-term memory.</p>
<h3>The Structured Summary</h3>
<p>A common mistake is asking for a generic summary ("User asked about code"). This is useless. We need a <strong>State Object</strong>.</p>
<p>Your summary instruction should look like this:</p>
<blockquote>
<p>"Compress the conversation history. Retain key variables, user preferences, and the current goal. Discard chit-chat."</p>
</blockquote>

<h3>The Summarization Cycle</h3>
<figure class="mermaid-diagram"><img src="/diagrams/llms-context-optimisation-p1-diagram-4.svg" alt="Diagram 4"></figure>
<p><strong>The Danger of Poisoning:</strong>
If the summarizer hallucinates (e.g., records "User is on Windows" instead of "macOS"), that hallucination becomes the <strong>Ground Truth</strong> for all future interactions. This is called <strong>Context Poisoning</strong>.</p>
<hr>
<h2>⚡ Caching: The Infrastructure Layer</h2>
<p>While we optimize the <em>content</em>, providers like Anthropic and OpenAI are optimizing the <em>delivery</em>.</p>
<h3>Prompt Caching (Anthropic/OpenAI)</h3>
<p>Traditionally, if you send a 10k token prompt, the GPU has to process all 10k tokens every time.</p>
<p><strong>Prompt Caching</strong> changes this. If the first 90% of your prompt (System Instructions + Few-Shot Examples + Documentation) is identical to the last request, the API can "hot-load" that pre-processed state from the cache.</p>
<p><strong>Key Insight for Engineers:</strong>
Structure your prompts like a layered cake.</p>
<figure class="mermaid-diagram"><img src="/diagrams/llms-context-optimisation-p1-diagram-5.svg" alt="Diagram 5"></figure>
<ol>
<li><strong>Static Layer (Cached):</strong> System Prompt, Tool Definitions, Docs.</li>
<li><strong>Dynamic Layer (Uncached):</strong> Recent Conversation History, User Query.</li>
</ol>

<h2>🚀 The "Reshape and Fit" Strategy</h2>
<p>So, which one do you use? The answer, as always in engineering, is "It Depends."</p>
<p>My recommendation for a production-grade agent is a hybrid approach I call <strong>Reshape and Fit</strong>:</p>
<ol>
<li><strong>Recent Buffer:</strong> Keep the last 5 turns exactly as they are (High Fidelity).</li>
<li><strong>Compaction:</strong> For turns 6-20, strip out all Tool Outputs but keep the function calls.</li>
<li><strong>Summarization:</strong> For turns 20+, compress into a "Golden Summary" object.</li>
<li><strong>Offloading:</strong> If a specific sub-task (like "Search Google") is complex, spawn a <strong>Sub-Agent</strong>. Give it a fresh context, let it do the messy work, and return <em>only</em> the final answer to the main agent.</li>
</ol>
<h3>The Final Stack</h3>
<figure class="mermaid-diagram"><img src="/diagrams/llms-context-optimisation-p1-diagram-6.svg" alt="Diagram 6"></figure>
<p>Context is not just a text box. It is the RAM of your AI application. Treat it with the same discipline you treat your database connections or memory heaps.</p>
